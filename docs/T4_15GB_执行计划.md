# Tesla T4 15GB 执行计划

日期：2026-10-20。范围：真实模型的量化工程验证。当前是计划，尚未在T4实测。

目标是用 **NF4权重量化 + FP16计算**，依次跑通 LLaDA 和 Dream 各20道工程题，验证真实去噪轨迹能够接入现有离线工具。先完成这40条轨迹及必要重复/对照运行；200题采集作为可选扩展。T4阶段不替代正式BF16实验。

## 1. 当前基础与需要补的工作

已有：冻结QA数据、smoke20、pilot200、统一NPZ轨迹校验、TRE/特征导出、LR/MLP和离线评测。

**尚无真实模型采集器。** `scripts/collect_llada.py`、`scripts/collect_dream.py` 是本计划拟新增的适配器，当前不能直接调用。不能把 `scripts/offline.py demo` 的模拟轨迹当作T4运行结果。

本计划默认Linux单卡实例；本地Windows继续负责离线处理。推荐主机RAM约32GB、持久磁盘剩余约60GB或更多，实际需求以下载清单和加载峰值为准。NF4是加载时量化，下载官方原始checkpoint仍需要原始权重的磁盘空间。

## 2. 固定配置

| 项目 | LLaDA | Dream |
|---|---|---|
| 模型 | GSAI-ML/LLaDA-8B-Instruct | Dream-org/Dream-v0-Instruct-7B |
| checkpoint/tokenizer revision | 08b83a6feb34df1a6011b80c3c00c7563e963b07 | 05334cb9faaf763692dcf9d8737c642be2b2a6ae |
| 权重 | bitsandbytes 4-bit NF4，double quantization | 同左 |
| 计算dtype | FP16；统计量FP32 | 同左 |
| Batch | 1 | 1 |
| 首次加载检查 | 1题，16输出位置/16步 | 同左，如实现支持 |
| smoke主配置 | 64输出位置/64请求步，单block=64 | 64输出位置/64请求步，单生成段 |
| 解码候选 | temperature=0，cfg_scale=0，low_confidence | temperature=0，alg=entropy，alg_temp=0，top_p/top_k不启用 |
| Seed | 20261020 | 同左 |
| Prompt | 冻结no-context内容 + 各自tokenizer的chat template | 同左 |
| 输入 | data/raw_qa/subsets/smoke20.jsonl | 同一文件、同一question_id |

Dream的单生成段记录为block_size=64是统一元数据语义，不能把未支持的block_size参数强塞给diffusion_generate。实际观测T、forward次数分别记录，不强行把终止行为改成固定64次。

解码参数在首轮源代码核对后冻结；若某参数不支持，记录实际协议并修订运行配置，不能静默忽略。后续BF16对照应保持该模型自己的解码协议一致。

量化配置的目标形式（仅为加载片段，不是完整采集脚本）：

```python
quantization_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.float16,
)
# AutoModel.from_pretrained(...,
#     revision=checkpoint_revision, trust_remote_code=True,
#     quantization_config=quantization_config,
#     torch_dtype=torch.float16, device_map={"": 0})
```

必须检查量化层实际存在、未量化层的dtype及device map。显式指定FP16，不能用dtype=auto继承checkpoint中的BF16。加载后不照抄普通模型的整体model.to(...)转换。T4硬件支持NF4，不代表两套自定义模型已通过bitsandbytes兼容性验证。[量化官方文档](https://huggingface.co/docs/transformers/quantization/bitsandbytes)

## 3. 阶段A：实例、环境和下载

1. 运行 `nvidia-smi`、`free -h`、`df -h`；记录GPU型号、实际可用显存、驱动、CPU RAM、持久目录。确认单卡没有其他大模型进程。
2. 保留现有CPU项目环境；额外用uv建两个独立的Python 3.11推理环境，例如 `.venv-llada-t4` / `.venv-dream-t4`。模型环境不改CPU项目的pyproject/uv.lock。
3. 候选版本：Dream从官方说明的torch 2.5.1、transformers 4.46.2起步；LLaDA从官方说明的transformers 4.38.2起步，torch先采用同一2.5.1系列。CUDA wheel选择与实例驱动兼容的版本；官方提供2.5.1的CUDA 12.1安装入口。[Dream说明](https://huggingface.co/Dream-org/Dream-v0-Instruct-7B) · [LLaDA说明](https://github.com/ML-GSAI/LLaDA) · [PyTorch安装档案](https://pytorch.org/get-started/previous-versions/)
4. accelerate/bitsandbytes选择与候选torch/transformers兼容的版本；先验证CUDA张量运算和一个Linear4bit forward，再冻结完整依赖清单。以上是待验证候选，不能写为“环境已通过”。若固定模型revision需要不同transformers版本，只在该模型环境做有日志的单项调整。
5. 将HF缓存放在实例的持久云盘，按已固定revision下载；确认分片完整、磁盘大小和文件校验。两模型共享缓存目录，分别顺序加载，不重复复制整份权重。

验收：CUDA/4bit算子可以运行、依赖和设备信息有记录、checkpoint完整且可按revision追溯。此阶段不要求也不执行基座训练、QLoRA或其他模型微调。

## 4. 阶段B：补齐最小采集适配器

每个适配器接收问题JSONL、模型/采样配置和输出目录，写统一trace-v1。使用LLaDA去噪循环、Dream diffusion_generate或其最小观测适配，不用普通自回归generate代替扩散解码。

采集顺序：

1. 保存本步更新前的MASK状态。
2. 模型forward；按该模型实现核对logits与位置的对应关系。
3. 在采样温度/噪声/过滤变换前，用FP32计算熵、top1概率和top1 token；只保留生成位置的统计量。
4. 完全按原解码语义选择并写入token，记录实际由MASK变为非MASK的位置。
5. 将小数组转CPU，保存NPZ；不跨步保留全词表logits、概率张量或计算图。

Dream重点检查hook收到的logits是否已经shift，避免重复或遗漏。LLaDA的cfg_scale固定0，避免额外无条件forward。单调揭示是trace-v1的前提；若所选实现真的重掩码已揭示token，必须换用已核验的单调揭示路径或先升级契约，不能伪造MASK/reveal字段来通过校验。

适配器还需提供：

- 原子落盘；中断恢复只跳过**哈希/配置一致且可重新读取校验**的已完成样本。
- 记录模型/代码/tokenizer revision、完整量化配置、dtype、环境、原始prompt与chat wrapper后的token IDs。
- 记录requested_steps、实际T/forward次数、EOS位置、有效长度、终止原因、耗时和显存allocated/reserved峰值。
- 真实量化轨迹设synthetic=false；precision可用统一的 `nf4_fp16`，同时分字段保存权重格式与compute dtype。不得只写fp16而隐去权重量化。

## 5. 阶段C：单题验证和观测无干扰验证

顺序：LLaDA加载→16/16单题→64/64单题→验证通过→阶段D→退出进程；再运行Dream。

单题验收：

- 单GPU实际4bit加载成功，未静默卸载到CPU/磁盘。
- 能生成、保存并由现有load_trace重新读取；所有统计有限且范围合理。
- MASK迁移、reveal_step、最终token与文本对应，EOS/空答案可解释。
- 同一模型、输入、seed、解码配置，比较采集开启/关闭的最终token；观测不能改变生成。若发现非确定性，重复定位并记录差异，未解决前不扩大规模。
- 进入循环前/后分别计时；用CUDA synchronize保证计时口径一致。清零后测实际峰值，并保留nvidia-smi快照，不能仅凭模型静态大小估显存。

若16/16能跑而64/64失败，只能算部分接口通过，不能声称主smoke配置已验收。

## 6. 阶段D：两模型各20题真实smoke

两模型依次处理完整smoke20，输出核心40条轨迹；另外每模型选3题重复运行，同seed复核token、reveal集合与统计量。

验收：

- 每个模型有20个不同question_id，集合与smoke20完全一致；失败样本、重试、缺失不能静默丢弃。
- 全部NPZ校验通过；人工抽查每模型至少5条去噪轨迹，覆盖早/中/晚步和EOS/边界案例。
- 汇总加载耗时、单题生成耗时均值/中位数、峰值显存、轨迹体积、失败/重试率和重复性。
- 生成质量只作异常诊断；不以20题正确率高低作为工程成功标准。

输出独立命名，例如：

```text
data/trajectories/t4_nf4_smoke20/{llada,dream}/<sample_id>.npz
data/generations/t4_nf4_smoke20.jsonl
data/manifests/t4_nf4_smoke20.json
reports/t4_nf4_smoke_report.md
```

配置改变须新run_id；缓存和上述结果目录都应位于持久盘，回传本地后再结束租用实例。

## 7. 阶段E：回本地接通离线链路

以下命令已由现有脚本支持，但输入必须先由采集器实际产生。smoke20只在子集文件内，因此label和extract都要显式传 --questions，不能依赖默认研究池查找。

```powershell
uv run python scripts/offline.py label --generations data/generations/t4_nf4_smoke20.jsonl --questions data/raw_qa/subsets/smoke20.jsonl --output data/labels/t4_nf4_smoke20.proposals.jsonl
uv run python scripts/offline.py extract --traces data/trajectories/t4_nf4_smoke20 --labels data/labels/t4_nf4_smoke20.proposals.jsonl --questions data/raw_qa/subsets/smoke20.jsonl --output data/features/t4_nf4_smoke20.parquet
```

检查TRE和基础特征的有限性、分布、长度/EOS关联；复核匹配提案。**smoke split不能用于训练或正式测试**；现有evaluate要求train/validation/test，故此时不调用它生成研究迁移矩阵。自动提案保留human_reviewed=false。

## 8. 可选扩展：quantized pilot200

只有两个模型都通过完整smoke、适配器稳定且单题成本可接受，才处理 `data/raw_qa/subsets/pilot200.jsonl`，每模型200题（120/30/50），共400条量化轨迹。不能用纯test的small200替代。

人工审核correct/incorrect并填写human来源；未审核/拒答/截断/格式失败保留类别并报告覆盖率。源train和validation必须有足够的两类样本，才训练LR/MLP；不能挪目标测试标签调阈值。样本不足时报告不足，必要时按冻结规则补源train/dev，不能凑一个矩阵数字。

产物仍全部独立放在t4_nf4_pilot200命名下。特征导出后，可用既有命令运行：

```powershell
uv run python scripts/offline.py evaluate --features data/features/t4_nf4_pilot200.parquet --output results/t4_nf4_pilot200 --feature-sets entropy_raw relative_normalized --bootstrap 500 --allow-nonbf16
```

它最多说明**此量化设置**下的探索结果，不证明BF16跨模型泛化。不得与BF16轨迹混成主表，也不应仅据量化负结果取消BF16主线。默认计划在40条smoke验收后结束，pilot200需要基于实测成本再决定。

## 9. 显存不足或兼容失败时的处理顺序

1. 清掉其他GPU进程的占用；确认batch1、单模型、eval/inference_mode、无梯度/attention/hidden-state/历史logits保存。
2. 确认真实Linear4bit覆盖和未量化层dtype，没有意外BF16或FP32全模型副本。
3. GPU上只对生成位置分块计算FP32统计；避免将全prompt的全词表logits转FP32后长期持有。保留原始解码结果，不复用统计量去改变采样。
4. 使用模型支持的PyTorch注意力实现；不为T4强制引入FlashAttention-2或自回归KV缓存优化。
5. 16/16仅用来定位。若64/64仍OOM，记录可通过的最大配置；不默默缩短后称64/64已成功。
6. 不默认转CPU/disk offload：这可能让程序可运行，却掩盖T4-only兼容性与吞吐。若需offload，应新建独立诊断配置。自定义模型若无法保持原语义接入4bit，则该模型T4项停止，移交4090D BF16。

NF4的8B理论权重数据约4GB只是下限，未包括量化元数据、未量化模块、激活、logits和框架开销；不能据此承诺显存峰值。留出运行余量，记录实际可用显存和峰值。

## 10. 时间、预算与最终交接

先测每模型5题的同配置耗时，记录加载与下载时间，不先承诺T4能在多少分钟采完。采集估时为 `20*t_llada + 20*t_dream`（秒），另加加载、重复/对照与I/O。若扩pilot200，按各自实测均时乘200。下载缓存可复用，但不能用16步结果外推64步后不作复验。

本阶段最终应交付：两套已冻结环境、可复用采集适配器、两模型各20条真实NF4轨迹、人工步骤抽查与资源报告、离线可读取特征、持久盘/本地双份结果及下阶段配置。

4090D阶段继续：相同问题与各自解码协议下的BF16 pilot、真实标签审核、正式pilot200和双向迁移矩阵；再决定是否扩到800–2000题。T4观察不能替代该验收。
